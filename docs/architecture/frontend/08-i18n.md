# 前端 08 — 國際化

## 1. 目標

| 項目     | 決定                                                            |
| -------- | --------------------------------------------------------------- |
| 支援語系 | `zh-TW`（預設）、`en-US`                                        |
| 函式庫   | i18next（**不用** react-i18next，自寫薄 hook）                  |
| 來源格式 | JSON，隨原始碼進版控                                            |
| 載入方式 | **按 feature 分包，隨路由載入**                                 |
| 語系偵測 | 使用者偏好（後端） → localStorage → `navigator.language` → 預設（§1.2） |

### 1.1 為什麼不用 react-i18next

react-i18next 會在每次語系變更時觸發大量重渲染，且它的 `Suspense` 整合與
TanStack Router 的 loader 機制重疊。我們的需求很單純：
「給我一個 `t()`，語系變了重渲染」。自寫的 hook 大約 40 行，訂閱 i18next 的
`languageChanged` 事件並觸發一次 re-render 即可。

### 1.2 偏好從哪裡來

語系與時區的值依序取第一個有的：

| 時機 | 來源 | 實作 |
| --- | --- | --- |
| 首次 render 前 | 本機存的（`preference` dictStorage）→ `navigator.languages` 對得到的語系 → 預設；不合法的值略過 | web-core `hydratePreferences()`、`detectBrowserLanguage()`、web-shared `resolveLanguage()` |
| profile 回來之後（backstage） | 帳號的 `user.preferences`，**與本機不同時以帳號為準**，並寫回本機（跨分頁同步） | web-core `applyAccountPreferences()`；backstage `features/account` 的 `useSyncAccountPreferences()`（掛在 `app/App.tsx`） |
| 被 backstage 導到 apps/platform 登入 | authorize 帶的 `ui_locales`（[`../04-sso.md`](../04-sso.md) §3.2） | backstage `features/auth/sso.ts`；apps/platform `features/login` 的 `useRequestedLocale()` |

- 帳號的值只在 **改變** 時套用：本機剛切換、同步帳號還沒完成時，期間重取到的舊 profile 不會把畫面切回去。
- 語系要對得到支援的語系（`en-GB` → `en-US`、`zh-Hant` → `zh-TW`），時區要 `Intl` 認得，才會套用。
- 平台管理者的帳號沒有存偏好（[`../04-sso.md`](../04-sso.md) §6.2），apps/platform 沒有第二列：只用本機的值與 `ui_locales`。
- 偏好頁的時區是完整、可搜尋的 IANA 清單（web-shared `supportedTimeZones()`，系統設定的預設時區用同一份）。
- 每個 API 請求以 `Accept-Language`（介面語系）與 `x-client-timezone`（IANA 時區）帶上目前的值（web-core `plugins/fetcher/client-preference.ts`）；送出當下讀 store，切換後下一個請求就是新值。

## 2. 語系包的分包

```
packages/web-core/src/locales/resources/{en_US,zh_TW}.json
                                                   全域：兩個 app 共用（common、error、validation、components、theme、language、realtime、layout、changePassword；job、auditLog 的共用部分）
app/locales/{en_US,zh_TW}.json                     全域：這個 app 專屬（menu、app、permission…），與上一行深層合併、同名鍵以 app 為準
features/auth/locales/{en_US,zh_TW}.json           scope: 'feature-auth'
features/user/locales/{en_US,zh_TW}.json           scope: 'feature-user'
features/role/locales/{en_US,zh_TW}.json           scope: 'feature-role'
features/permission/locales/…                      scope: 'feature-permission'
features/account/locales/…                         scope: 'feature-account'
features/audit-log/locales/…                       scope: 'feature-audit-log'
plugins/features/*/locales/…                       各自的 scope
```

### 2.1 註冊（plugin 的 `onInit`）

```ts
await appContext.addResourceBundle(
  {
    [Languages.EN_US]: { [LanguageNamespace.TRANSLATE]: () => import("./locales/en_US.json") },
    [Languages.ZH_TW]: { [LanguageNamespace.TRANSLATE]: () => import("./locales/zh_TW.json") },
  },
  { scope: ROLE_LOCALE_SCOPE },
);
```

傳的是 **動態 import 的函式**，不是 JSON 內容。註冊只是登記「這個 scope 有這些
包可以載」，實際下載還沒發生。

全域語系包由 i18n plugin 登記：app 的 `plugins/app/i18n.ts` 呼叫 web-core 的 `i18nPlugin({ locales })`，傳入自己的 `app/locales/*.json`；
plugin 以 `mergeLocaleImporters(CORE_LOCALES[lang], locales[lang])` 把兩份合成一包（`@b2b-system/web-core/locales`），在首次 render 前載入。

| 字串屬於 | 放在 |
| --- | --- |
| web-core 的元件與機制（`RichTable`、頂列工具、錯誤頁、變更密碼、背景工作與稽核的列表、錯誤碼、驗證訊息、通用按鈕） | `packages/web-core/src/locales/resources/*.json` |
| 只有某個 app 用、但不屬於任何 feature（選單、品牌、權限名稱） | 該 app 的 `app/locales/*.json`；要改共用字串在某個 app 的措辭時也在這裡覆寫同一個鍵 |
| 某個 feature | `features/<name>/locales/*.json` |

### 2.2 載入（route 的 `loader`）

```ts
export const RoleListRoute = createRoute({
  path: "/role",
  loader: localeScopeLoader(ROLE_LOCALE_SCOPE),
  // …
});
```

`localeScopeLoader(scope)` 回傳一個 loader：

```ts
export function localeScopeLoader(scope: string) {
  return async () => {
    await loadLocaleScope(scope, i18n.language);
  };
}

const loaded = new Set<string>(); // `${scope}:${lang}`

export async function loadLocaleScope(scope: string, lang: string) {
  const key = `${scope}:${lang}`;
  if (loaded.has(key)) return;
  const importers = registry.get(scope)?.[lang] ?? {};
  await Promise.all(
    Object.entries(importers).map(async ([ns, importer]) => {
      const mod = await importer();
      i18n.addResourceBundle(lang, ns, mod.default, true, true);
    }),
  );
  loaded.add(key);
}
```

**效果**：`features/role/locales/*.json` 不在首屏 bundle 裡，第一次進入 `/role`
時才下載，且在頁面渲染 **之前** 就緒（loader 會 await），不會閃出原始 key。

上面是簡化過的版本，實際的 `loadLocaleScope`（`web-core/locales/i18n.ts`）另外處理：

| 情況 | 行為 |
| --- | --- |
| scope 還沒登記（可啟用的 feature 尚未安裝，[`frontend/02-plugin-system.md`](02-plugin-system.md) §9） | 不記成已載入，記成 **待載入**；該 scope 之後以 `addResourceBundle` 登記時立刻補載 |
| 同一包同時被要求 | 共用同一次下載 |
| 下載完成 | 通知 `subscribeLocaleScopeLoaded()` 的訂閱者。`useTranslation` 訂閱它：載入的是 **目前語系** 的包時，已經掛上的元件重渲染並拿到新的 `t`（以 `t` 為依賴的 memo 跟著重算），在路由之外顯示其他 feature 文字的元件（偏好頁的分頁與列表名稱、頂列的鈴鐺與批次佇列）才不會停在 key，也不必自己重繪 |

`useTranslation()`（`web-core/locales/useTranslation.ts`）回傳的 `t` 在字串沒變時維持同一個參考；**切換語系** 或 **目前語系的語系包載入完成** 時換新。
切換語系時（§2.3）先補載的各包是別的語系，不觸發重繪；最後的 `languageChanged` 才重繪一次——造訪過 N 個 feature 後切換語系，仍然只有一波整頁重繪。

### 2.3 切換語系時

`changeLanguage(lang)` 會：

1. **重新載入所有已載入過的 scope 的新語系版本**（走同一個 `loadLocaleScope`）
2. 全部到齊後才 `i18n.changeLanguage(lang)`：畫面一次換成新語系，不會先閃出 key
3. 寫入 `localStorage` 與後端偏好（`PATCH /auth/profile`）

第 1 步容易漏：只切 i18next 的語系而不補載已進入過的 feature 語系包，那些頁面
會退回 key 或 fallback 語系。

第 3 步由 `features/account` 的 `useChangeLocale()` 負責（寫 `useLocaleStore` → `changeLanguage` → 同步帳號），
兩個入口共用它：

| 入口 | 位置 | 行為 |
| --- | --- | --- |
| 頂列語言按鈕 | `web-core/layout/LanguageMenu.tsx`（app 的 `app/layouts/LanguageMenu.tsx` 傳入 `onChange`：backstage 用 `useChangeLocale`，apps/platform 不同步到帳號） | 支援的語言（`SUPPORTED_LANGUAGES`）剛好兩種時按一下直接切到另一種（`language-toggle`）；超過兩種改成下拉選單（`language-menu-trigger`）；只有一種時不顯示 |
| 偏好頁 | `features/account/pages/Preference` | 下拉選單；同步到帳號成功才顯示「已儲存」，失敗顯示錯誤提示（頂列的語言按鈕失敗時同樣顯示錯誤） |

語言名稱在 `LANGUAGE_LABELS`（`packages/web-shared/src/constants/lang.ts`），一律用該語言自己的寫法、不翻譯，
看不懂目前介面語言的人才找得到自己的語言。

## 3. Key 命名

```
<domain>.<scope>.<name>
```

| 類別         | 範例                                                                    |
| ------------ | ----------------------------------------------------------------------- |
| 全域通用     | `common.save` / `common.cancel` / `common.delete` / `common.confirm`    |
| 選單         | `menu.user` / `menu.role` / `menu.auditLog`                             |
| 錯誤碼       | `error.AUTHZ_FORBIDDEN` / `error.ROLE_NAME_DUPLICATE`                   |
| 權限名稱     | `permission.role.grantPermission` / `permission.resource.user`          |
| Feature 頁面 | `role.list.title` / `role.create.submit` / `role.detail.tab.permission` |
| Feature 訊息 | `role.create.success` / `role.delete.confirm`                           |
| 欄位標籤     | `role.field.name` / `user.field.email`                                  |
| 狀態值       | `user.status.active` / `user.status.locked`                             |

### 3.1 錯誤碼與權限名稱的特別約定

這兩類 key 對應 **後端定義的值**，但都不在前端組字串
（[`coding-standards/06-literal-strings.md`](../../coding-standards/06-literal-strings.md)）：

```ts
t(ERROR_MESSAGE_KEY.AUTHZ_FORBIDDEN); // 對照表：web-core/errors/errorMessageKey.ts
t(permission.nameI18nKey); // 後端回傳完整 key：permission.role.grantPermission
```

因此：

- 新增一個後端錯誤碼 → 必須同時在 web-core 的 `ERROR_MESSAGE_KEY` 與 `packages/web-core/src/locales/resources/*.json` 加 `error.<CODE>`（`ERROR_MESSAGE_KEY` 以 `satisfies Record<ErrorCode, …>` 宣告，漏了編譯失敗）；兩個 app 都不必改
- 新增一個權限 → 必須同時在該 app 的 `app/locales/*.json` 加 `permission.<resource>.<action>`

沒加的話 `t()` 會回傳 key 本身（錯誤碼不在對照表時則拿不到 key）。`useErrorMessage()` 偵測到這兩種情況時
退回通用訊息，所以不會在畫面上顯示 `error.SOMETHING_WEIRD`——但這代表缺翻譯會
靜默降級，所以 **CI 有檢查**：`packages/web-core/src/locales/__tests__/resources.test.ts` 直接讀 `@b2b-system/error-codes` 的 `ALL_ERROR_CODES`
（不手抄清單），確認每一項都在 `ERROR_MESSAGE_KEY` 與兩個語系檔中；各 app 的 `app/__tests__/locales.test.ts` 比對權限名稱與 `PERMISSION_SEED` 的清單，
以及自己兩個語系檔的鍵集合。

`useErrorMessage()` 會把錯誤 `details` 的字串與數字值當插值參數（例：`ROLE_IN_USE` 的 `{{userCount}}`）。

### 3.2 表單驗證訊息（Zod）

Zod 的預設訊息是英文技術字串。i18n plugin 初始化時呼叫 `configureZodErrorMap()`（`web-core/locales/zodErrorMap.ts`，
兩個 app 共用），依 issue code 對應到 `validation.*`，在驗證當下以目前語系翻譯。
`.refine()` 不寫死 `message`，改用 `params: { messageKey: 'validation.xxx' }`。

### 3.3 設計系統元件的預設文案

`@b2b-system/ui` 不依賴語系，預設文案（必填、Select 的搜尋／無結果／載入中、Toast 的關閉、分頁的名稱、
日曆切換月份的按鈕、日期選擇器的清除與開啟、TreeEditor 的工具列與空狀態、Spinner 的「載入中」）寫死成繁中；
`web-core/shell/ComponentLabelsHost.tsx` 以 `ComponentLabelsContext`（`@b2b-system/ui/labels`）傳入目前語系的 `t()`，
元件在呼叫端沒有明確傳入時用 context 的值。context 另外帶目前的介面語系（`locale`），日曆的月份標題與星期依它格式化。

context 涵蓋的文案，`features/` 不必再傳；新增有預設文案的元件時，優先把文案加進 `ComponentLabels`
（web-core 的語系檔放 `components.*`），而不是要求每個呼叫端傳 `labels`。

### 3.2 表單驗證訊息（Zod）

Zod 的預設訊息是英文技術字串（`Too small: expected string to have >=1 characters`）。
i18n plugin 初始化時以 `configureZodErrorMap()`（`web-core/locales/zodErrorMap.ts`）設定 Zod 的全域 `customError`，
依 issue 的種類對應到 `validation.*`（`required`、`email`、`tooShort`、`tooLong`、`format`、`invalid`），
翻譯在驗證當下才做，切換語系後下一次驗證就是新語言。

- Schema 不寫 `message`；寫了就會蓋過語系訊息。
- `.refine()` 的訊息用 `params: { messageKey: 'validation.passwordMismatch' }` 帶完整的語系鍵。
- 兩個 app 都經由 web-core 的 `i18nPlugin` 設定；`validation.*` 在 web-core 的語系檔，app 專屬的（例：backstage 的 `validation.usernameTooShort`）放 app 的 `app/locales`。

## 4. `useTranslation()`

```ts
// web-core/locales/useTranslation.ts
export function useTranslation() {
  const [, force] = useReducer((n) => n + 1, 0);
  useEffect(() => {
    i18n.on("languageChanged", force);
    return () => {
      i18n.off("languageChanged", force);
    };
  }, []);
  return {
    t: i18n.t.bind(i18n),
    language: i18n.language,
    changeLanguage,
  };
}
```

### 4.1 型別安全

透過 declaration merging 累積各 feature 的資源型別：

```ts
// 各 feature 的 plugin.ts
declare module "@b2b-system/web-core/locales" {
  interface LocaleResourceMap {
    feature_role: typeof import("./locales/en_US.json");
  }
}
```

`web-core/locales` 把 `LocaleResourceMap` 展平成一個 key 聯集型別餵給 i18next 的
`CustomTypeOptions`，於是 `t('role.list.titl')` 會編譯失敗。

**en_US 是型別來源**，因此 en_US 是「規範」語系：先寫它，zh_TW 對齊它。
另有測試斷言兩個檔案的 key 集合相同（web-core 的語系檔與各 app、各 feature 的各自比對；複數後綴 `_one`／`_other` 視為同一個鍵）。

## 5. 格式化

| 對象     | 作法                                                                     |
| -------- | ------------------------------------------------------------------------ |
| 日期時間 | `@b2b-system/web-shared/date` 的 `formatDateTime()`／`formatDate()`：預設的語系與時區由 i18n plugin 依偏好（`useLocaleStore`、`useTimezoneStore`）以 `setDateTimeDefaults()` 設定；不合法的時區退回 `Asia/Taipei`。日期篩選與到期日的日界線用 `zonedDayBoundary()`、日期選擇器的「今天」與最早日期用 `todayInZone()`（同一個時區）；不用 `dayjs()`／`new Date()` 的本地日期——那是瀏覽器的時區 |
| 數字     | `Intl.NumberFormat(i18n.language)`                                       |
| 相對時間 | `dayjs` 的 `relativeTime` plugin（稽核日誌的「3 分鐘前」）               |
| 複數     | i18next 的 `_one` / `_other` 後綴：英文兩個都要，中文的複數規則只有 `other`，只放 `_other`；呼叫端一律傳 `count`（數字）。錯誤訊息的數量在 details 裡另有欄位名（`ROLE_IN_USE` 的 `userCount`），`useErrorMessage()` 依 `ERROR_COUNT_DETAIL` 另外以 `count` 傳入 |
| 清單     | web-shared `formatList(items, language)`（`Intl.ListFormat`）：中文「A、B和C」、英文「A, B, and C」；不寫 `join('、')` |
| 標點組句 | 「名稱（說明）」「欄位：值」也是語系的事：`common.withNote`、`common.labelValue`、`common.labelColon`、`common.parenthetical`、`common.withDescription`（web-core），不在程式裡寫 `（）：｜` |
| 頁面語系與標題 | i18n plugin 在初始化與切換語系時設定 `<html lang>`（`HTML_LANG`：`zh-Hant`／`en`，報讀器依它選語音）；`document.title` 由 web-core/shell 的 `DocumentTitle` 依路由的 `staticData.titleKey` 設成「頁面 · 產品名」（app 的 `App.tsx` 掛上，產品名的鍵由 app 傳入） |

```json
// en_US.json
{ "user.batch.delete.success_one": "Deleted {{count}} user.", "user.batch.delete.success_other": "Deleted {{count}} users." }
// zh_TW.json
{ "user.batch.delete.success_other": "已刪除 {{count}} 位使用者。" }
```

`t('user.batch.delete.success', { count })` 依語系挑後綴。各 app 的 `locales.test.ts` 與 web-core 的 `resources.test.ts`
檢查英文含 `{{count}}` 的鍵都有 `_one`／`_other`、中文有 `_other`；鍵集合的比對把複數後綴視為同一個鍵（web-core/testing 的 `pluralProblems`、`localeKeySet`）。
單複數之外句型也不同時（「每天」與「每 2 天」）用兩個鍵、變數不叫 `count`（公告的週期摘要）。

**時區**：後端一律以 UTC 儲存與傳輸（ISO 8601 帶 `Z`），前端在顯示的那一刻才
轉成使用者偏好的時區。任何把時區邏輯寫進 adapter 或 API 層的做法都是錯的。
請求帶的 `x-client-timezone`（§1.2）只是告訴後端使用者在哪個時區，不改變傳輸格式。

## 6. 檢查清單

- [ ] `en_US.json` 與 `zh_TW.json` 的 key 集合完全相同（有測試）
- [ ] 每個後端 `ErrorCode` 都有 `error.<CODE>`（有 CI 檢查）
- [ ] 每個權限都有 `permission.<resource>.<action>`（有 CI 檢查）
- [ ] feature 的語系包都帶了 `scope`，且對應 route 掛了 `localeScopeLoader`
- [ ] 沒有任何 JSX 裡寫死的中文或英文字串（lint 規則掃描）
- [ ] 程式碼（註解以外）沒有寫死的中文標點 `、（）：｜`（各 app 與 web-core 的 `full-width-punctuation.test.ts`；給開發者的 `throw new Error` 除外）
- [ ] 帶數量的句子有複數形（有測試）；入口 route 有 `staticData.titleKey`（有測試檢查翻譯存在）
- [ ] 切換語系後，已造訪過的頁面文字全部跟著換（手動驗收項）
