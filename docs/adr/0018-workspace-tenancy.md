# ADR-0018 — 工作區：權限鍵分範圍 × 工作區角色 ＋ 工作區內的資源授權

- 狀態：**被取代**（[ADR-0020](./0020-physical-tenant-isolation.md)：改為每租戶一個 database 與網域；本文件保留作為評估紀錄）
- 日期：2026-09-29
- 相關：[ADR-0006](./0006-flat-permission-scope.md)（取代其「多租戶」延伸路徑）、[ADR-0015](./0015-file-folder-access.md)（實現其「專案成為資料夾的上層」）、
  [ADR-0017](./0017-mail-delivery.md)（邀請信）、`features/workspace.md`（已刪除）

## 背景

所有資料目前都在同一個全域範圍。遊戲編輯器上線後，一定會有「專案」這個單位，
不同專案的成員、資源、權限要互相隔離。ADR-0015 也寫明資料夾將來會掛在專案底下。

越晚做，要改的地方越多：每張業務表都要加 `workspace_id`，
權限快取的 key、推播的 room、稽核的篩選條件也要跟著改。
所以要在第一個編輯器功能之前定案。

有兩個前例的設想並不一致：

- ADR-0006 的延伸路徑：`user_roles` 加上作用域，也就是 **角色 × 範圍**。
- ADR-0015 的延伸：專案當成 `resource_grants` 的一種節點，成員就是專案上的等級授權，也就是 **資源 ACL**。

## 決定

### 授權模型

| 方案 | 代表 | 結論 |
| --- | --- | --- |
| A. 只有資源 ACL：工作區是 `resource_grants` 的節點，成員 = 四個等級之一 | Google Drive | 不採用：編輯器會有上百個動作，四個等級太粗；「美術」「企劃」這種職能分工需要權限鍵 |
| B. 只有工作區角色：`user_roles` 帶 `workspace_id` | K8s RoleBinding、GitHub Org | 不採用：沒辦法細到單一資料夾或關卡，ADR-0015 已經證明需要資源 ACL |
| **C. 兩層並用** | GCP IAM（專案角色 ＋ 資源 IAM）、Notion | **採用**：工作區角色決定能做「哪些種類」的事；`resource_grants` 決定在工作區內能碰「哪幾個」資源 |
| D. ReBAC 服務（OpenFGA） | Zanzibar | 延後：理由與 ADR-0015 相同 |

### 隔離方式

| 方案 | 結論 |
| --- | --- |
| **A. 共用資料表 ＋ `workspace_id` 欄位，由應用層強制** | **採用** |
| B. A ＋ Postgres Row-Level Security 當第二道防線 | 延後：連線池和背景工作都得改成每個交易 `SET LOCAL`，而且需要一條繞過 RLS 的路徑給維護工作。改在 D10 用組合外鍵、型別與測試補強。遇到 `multi-instance` 或原生 SQL 變多時再評估 |
| C. 每個租戶一個 schema／資料庫 | 不採用：migration 要跑 N 次；跨工作區的平台管理（使用者、稽核）會變得很難寫 |

### 具體決定

| # | 決定 | 理由 |
| --- | --- | --- |
| D1 | **工作區就是專案**，這一版只有一層；工作區底下不再分專案 | 在編輯器出現之前，猜不出第二層該是什麼（ADR-0006 理由 1）。真的需要時，工作區內的專案當作 `resource_grants` 的一種節點，不會動到租戶邊界 |
| D2 | 權限鍵加上 **範圍**（`permissions.scope`）：`platform`（使用者、角色、權限目錄、稽核、系統、審批、背景工作、工作區管理）或 `workspace`（檔案、成員管理、未來的編輯器）。鍵的字串格式不變 | 如果不分範圍，全域角色持有的 `file:access` 會對每個工作區都生效，隔離就失效了。字串格式不變，ADR-0006 的相容性承諾仍然成立 |
| D3 | 角色也有範圍（`roles.scope`）。角色只能含同範圍的權限鍵，以 service 檢查 ＋ DB trigger 雙重把關。**角色定義全域共用**，指派則分工作區；**不做**工作區自訂角色 | 角色管理與反提權仍然只有一套。將來要做自訂角色時，加上可為空的 `roles.workspace_id` 即可，向後相容 |
| D4 | 使用者在工作區 W 的權限集合：`P(u, W)` = 全域角色的 platform 鍵 ∪ 他在 W 的工作區角色的 workspace 鍵 | 只有聯集、沒有 deny，延續 ADR-0006 理由 4 |
| D5 | **只有 super-admin 能看到任何工作區的內容**。持有 `workspace:*` 的平台管理員只能管理工作區本身（清單、名稱、成員與角色），看不到裡面的檔案或編輯器資料；要看就得被加為成員，而加成員會留下稽核 | 工作區隔離對平台管理員也要有意義。super-admin 本來就會繞過所有檢查（`01-domain-model.md` §6.2） |
| D6 | 稽核不算「內容」：平台的 `auditLog:read` 可以看到所有工作區的稽核紀錄。`audit_logs` 加可為空的 `workspace_id` 供篩選 | 稽核是平台監督用的；紀錄只有名稱快照與變更摘要，不含檔案內容 |
| D7 | 資料夾 ACL 疊在工作區角色上面：能力 = `P(u, W)` 有 `file:X` ∨ 資料夾等級允許 X。**資料夾樹以工作區為根**；工作區內的 `file:*` 等於「這個工作區的所有資料夾」 | 就是 ADR-0015 D1，範圍從全站縮小到工作區。`FileAccessService` 只需要把權限集合換成 `P(u, W)` |
| D8 | 請求以 **路由前綴** `/workspaces/:workspaceId/...` 帶工作區；工作區 **不放進 JWT** | 同一個人可以在兩個分頁開不同的工作區，所以工作區是請求的屬性，不是身分的一部分。前綴讓稽核、快取、日誌都看得到工作區 |
| D9 | 工作區範圍的 controller 用 `@WorkspaceScoped()` 標記。guard 依序：確認成員資格（不是成員回 **404**，不洩漏工作區是否存在）→ 解析 `P(u, W)` → 把 `WorkspaceScope` 放進 request。`route-audit` 在啟動時多檢查一條：workspace 範圍的鍵只能宣告在 `@WorkspaceScoped` 路由上，反之亦然 | 延續「宣告錯誤就讓程序啟動失敗」的做法 |
| D10 | 應用層隔離的三道防線：① **組合外鍵** `(workspace_id, x_id) → x(workspace_id, id)`，讓 DB 保證跨表引用不會跨工作區；② repository 的工作區方法第一個參數是 `WorkspaceScope`，這是品牌型別，只有 guard 能產生；③ 整合測試：對每個工作區路由帶另一個工作區的 id 呼叫，一律回 404 | 取代 RLS（見「隔離方式」） |
| D11 | 成員資格與角色指派分成兩張表：`workspace_members`、`workspace_member_roles`；後者以組合外鍵 cascade 到前者。**不在** `user_roles` 加 `workspace_id` | 主鍵欄位不能是 null；而且移除成員時角色會跟著消失 |
| D12 | 每個工作區至少要有一個持有 `workspaceMember:assignRole` 的成員，由 service 拒絕違反的操作（比照 I8）。如果最後一位管理員被刪除了，平台的 `workspace:update` 可以重新指定管理員，並留下稽核 | 避免出現沒有人能管理的工作區 |
| D13 | 建立工作區時要指定第一位管理員，給他系統角色 `workspace-admin`。這一步豁免反提權，因為建立者在新工作區裡沒有任何權限 | 冷啟動的唯一例外，只限這個系統角色 |
| D14 | **Email 邀請**：`workspaceMember:create` 可以用 email 邀請，邀請時一併指定工作區角色（受反提權限制）。收件人點信中連結後：如果已有帳號，就以該帳號登入並接受；如果還沒有帳號，就設定密碼、建立已啟用帳號並加入工作區。**邀請沒有帳號的 email 時，邀請人另外需要平台的 `user:create`** | 讓已有帳號的人加入工作區，是工作區內部的事；建立平台帳號則是平台層級的決定，不能透過工作區繞過註冊審批（反提權的精神）。持有連結就證明擁有該信箱，所以新帳號不必再走啟用流程 |
| D15 | 權限快取的 key 改成 `userId:workspaceId`（平台層級用 `userId:-`），並維護 `userId → keys` 的索引，讓 `invalidateUser` 能清掉這個人在所有工作區的項目。另外新增 `invalidateWorkspace` | 失效順序不變：交易之後清快取，然後才發佈事件 |
| D16 | 推播：工作區的 room 叫 `ws:{id}:perm:{key}`；**連線時加入所屬每個工作區的 room**（依在各工作區的權限），成員資格或權限變了就重算。工作區範圍的變更必須帶 `workspaceId`，沒帶就不推給任何工作區的 room。平台的 room 不變。不是成員的 super-admin 不加入那些工作區：瀏覽時由重新聚焦的重抓更新 | 前端只有 leader 分頁持有連線，代表所有分頁，而各分頁可能開著不同的工作區，所以不能只訂閱「目前的」工作區（原本設想的 `workspace.subscribe` 因此不採用）。前端的 query key 帶工作區、以 key 前綴失效，收到別的工作區的變更只會把沒在用的快取標成 stale |
| D17 | 前端：工作區頁面的網址是 `/w/:workspaceSlug/...`；目前工作區 **從 URL 推導**。工作區範圍的 query key 包含 `workspaceId`，所以切換工作區時不必清掉整個快取。`can()` 判斷「platform 鍵 ∪ 目前工作區的鍵」。頁面註冊時標 `scope: 'workspace'`：根版面只守平台頁面，工作區頁面由工作區版面在載入該工作區的權限後守。登入後預設開啟最近進入的工作區（`workspace_members.last_accessed_at`） | 連結可以直接分享、多分頁互不干擾；切回原本的工作區時快取還能命中。根版面若也等工作區的權限，會擋住負責載入它的工作區版面 |
| D18 | 遷移：建立預設工作區 `default`，把現有的資料夾、檔案、檔案類審批全部歸進去，所有使用者成為成員；含工作區範圍權限鍵、或是資料夾授權對象的角色，另建一個工作區角色承接（系統角色對應到 `workspace-admin` / `workspace-member` / `workspace-viewer`），持有者在預設工作區取得它、資料夾授權改指向它（見 `features/workspace.md`（已刪除） 開放問題 4） | 不刪資料、不讓任何人失去原本的存取；只看權限鍵會漏掉「沒有權限鍵、只當資料夾授權對象」的角色 |

## 代價

| 代價 | 評估 |
| --- | --- |
| 既有的自訂角色如果同時含兩種範圍的鍵，遷移時會被拆成兩個角色 | 角色名稱會多出「(工作區)」後綴；遷移時寫稽核，管理員之後可以改名 |
| 每張業務表多一欄、多一組組合外鍵與索引 | 這是隔離的必要成本；組合外鍵本身就是 DB 保證 |
| 工作區內的每個請求都要多確認一次成員資格 | 和權限集合一起快取，同樣受 `PERMISSION_CACHE_TTL` 控制 |
| 沒有 RLS：如果某個查詢忘了帶 `workspace_id`，DB 不會攔 | `WorkspaceScope` 型別加上越權測試；組合外鍵擋住跨工作區的引用 |
| 平台管理員不能直接協助處理工作區內的檔案 | 刻意的設計（D5）。需要時由 super-admin 處理，或讓平台管理員暫時成為成員，這會留下稽核 |
