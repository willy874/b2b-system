# best-practice

本專案的寫程式規範全部放在 **`docs/conventions/`** 資料夾。
這個 skill 不列出個別規則檔——規則會持續增加，**一律以資料夾當下的內容為準**。

## 1. 載入規則

1. 用 Glob 列出 `docs/conventions/**/*.md`，取得當下所有規則檔。
2. 先讀資料夾的 `README.md`：它說明規則強度標記（🔒 工具強制／👀 靠 review）與章節索引。
3. 讀 **所有** 其餘規則檔，不要只挑檔名看起來相關的——一條規則常同時影響前端、後端與測試。
   檔案多到不適合全讀時，至少讀完每個檔案的第 1 節（規則本身）與「檢查方式」一節。
4. 規則檔內連到 `docs/architecture/`、`docs/rbac/`、`docs/adr/` 的章節，需要細節時再跟著讀。

不要憑記憶套用規則；每次使用都重新列資料夾，才會拿到新增或修改過的規則。

## 2. 寫程式時

- 動手前先確認要改的檔案屬於哪一層（package／資料夾），依對應的依賴規則決定可以 import 什麼、邏輯該放哪一層。
- 規則附有 ✅ 寫法或範例時，照範例的形狀寫。
- 規則與使用者的要求衝突時，先說明衝突並詢問，不要默默違反或默默忽略使用者。
- `docs/architecture/` 與 `docs/conventions/` 衝突時以 `architecture/` 為準，並告知使用者 conventions 需要修正。

## 3. Review／自我檢查

完成修改後（或使用者要求檢查時）：

1. 逐一對照每個規則檔，檢查 **這次改動到的程式碼**。
2. 規則檔有「檢查方式」一節時，執行其中的指令；把路徑範圍縮到改動的檔案或資料夾，避免被既有違規淹沒。
3. 標為 🔒 的規則交給對應工具驗證（`pnpm typecheck`、`pnpm lint`、`pnpm test` 等），不要只靠目測。
4. 回報格式：每一項違規寫出 `檔案:行號`、違反的規則（`docs/conventions/<檔名>` §節次）、建議改法。
   沒有違規就明說沒有，並列出實際檢查過哪些規則檔。

## 4. 既有違規

規則檔的「現況」一節列出規則建立前就存在的違規：

- 不要把沒被這次改動碰到的既有違規當成新問題回報。
- 這次改動碰到那些檔案時，順手遷移，並從「現況」表中刪除對應的列。
- 發現「現況」沒列到的既有違規，回報給使用者，由使用者決定是否補進表中。

## 5. 新增或修改規則

使用者要新增規則時，照 `docs/conventions/README.md` 的「新增規則」一節，
在 `docs/conventions/` 新增檔案並更新該 README 的章節表。**不需要、也不應該修改這個 SKILL.md。**
